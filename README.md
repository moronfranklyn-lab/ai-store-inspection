# AI 巡店 · 排面缺货识别

> 一个**单功能**的 AI 产品案例：从业务口径定义 → 技术可行性验证 → 依据实测数据推翻自己的设计。

某休闲零食连锁门店的 AI 巡店项目。我负责其中的**一个检查项**——「**排面缺货识别**」（`SHELF_OOS`）的完整产品设计。

---

## 核心结论

**原设计**：AI 识别缺货并给出是**哪一层**，专员复核。
**实测之后**：模型判断"**有没有缺货**"可靠，判断"**是哪一层**"不可靠。**于是我改了自己的设计。**

| 维度 | 实测结果 | 产品含义 |
| --- | --- | --- |
| 判断"有没有缺货" | 结论一致性 **91.7%** | 可靠 —— 可以承担"从一堆照片里挑出有问题的" |
| 判断"缺的是哪一层" | 层级准确率 **60%** | **不可靠 —— 原设计"按货架层报告"被数据推翻** |
| 单次调用可用性 | 层号噪声率 **13.3%** | 单次调用不可采信，必须多次采样取多数 |
| 模型主动认怂 | 36 次判定中 **0 次**标"不确定" | 安全阀必须由产品侧强制，不能靠模型自觉 |
| 检查项边界 | 越界项只进备注、不进判定 | 用提示词把边界写清，模型能守住 |

修正后的设计：**AI 定位到"证据照片＋货架区域"，层号降级为辅助提示。**
理由：约 40% 的情况层号会报错，店长照着错层号白跑一趟，然后就不再信任这个功能。

## 这个案例里我做了什么（边界诚实）

**我做的**

- 把模糊的业务诉求（"货架没摆满"）翻译成结构化、可执行、可验收的检查项定义
- 设计"AI 初筛 + 人工复核"的产品链路与复核交互，并明确与既有巡店体系的边界
- 独立搭建评测链路，用真实数据验证最可能失败的假设
- **依据实测数据推翻并修正自己的产品设计**
- 制定效果评估方案（含合格标准与不达标时的处置）

**不是我做的（不据为己有）**

- 巡店系统的整体架构、任务派发、整改与申诉链路
- 其他检查项的 AI 化
- 团队组织、上线节奏、跨部门协同
- 模型选型的最终决策与商务

## 关于数据：本仓库不含任何前雇主资产

实验使用了真实门店照片与内部系统界面，但它们**不在本仓库中**：

- ❌ 门店巡店照片（含门店现场、品牌标识、可能含顾客与员工影像）
- ❌ 巡店系统截图（含内部结构与真实人名）
- ❌ 巡店检查表原文

原因见 [`作品集/03-合规说明.md`](./作品集/03-合规说明.md)。

**但本仓库引用的核心指标都不依赖这些数据**——它们是"模型自己跟自己比"得出的（一致性、噪声率、标注率），不需要人工基准。

要复现实验，按 `experiment/README.md` 准备自己的照片并配好 API Key 即可。

## 快速开始（跑评测链路）

```bash
cd "项目开发助手_副本2/ai-product-starter-kit-main 2/experiment"

# 不需要 Key 和照片：先验证流程
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest tests -q          # 20 项自检
.venv/bin/python -m oos_check.run --dry-run  # 用模拟响应跑通链路

# 接入真实模型
cp .env.example .env                          # 填入自己的 API Key（不会进仓库）
.venv/bin/python -m oos_check.probe           # 先探测哪些型号可用
.venv/bin/python -m oos_check.run --photos /path/to/photos
```

> 提醒：**换模型或换账号前先跑 `probe`**。实测中「最新版」型号名（`-latest` 后缀）在部分账号下会返回 403，而基础型号可用。
