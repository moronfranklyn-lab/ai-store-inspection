# 案例总览 · 排面缺货识别的 AI 化改造

| 项 | 内容 |
| --- | --- |
| 行业 | 休闲零食连锁零售 |
| 业务场景 | 门店标准化巡店（总部对加盟门店的强管控体系） |
| 我的角色 | **单功能产品经理** —— 只负责「排面缺货识别」这一个检查项 |
| 负责范围 | 判定口径定义、识别结果的产品形式、复核交互、效果验收与上线后迭代 |
| 不负责范围 | 其他检查项、巡店任务派发与整改链路、得分与考核规则、实时视频巡检、项目上线节奏 |

---

## 一、业务背景

### 1.1 这套系统在解决什么

连锁零食品牌走的是**加盟模式 + 总部强管控**路线，门店规模数千家。总部要确保每一家加盟店都达到统一的门店标准化基准，而手段是**巡店**：

- 总部设有专门的**门店标准化部门**（数百人），分**远程巡店**与**现场巡店**两队
- 巡店发现问题 → 转成整改任务下发门店 → 门店确认整改 → **门店可申诉** → 突发因素可报备
- 巡店结果直接关联门店的奖励与处罚

### 1.2 远程巡店的痛点：人看不过来

远程巡店专员的核心工作是**逐张翻看门店上报的巡店照片**，凭经验判断哪些项不合格。

- 单个专员负责数十家门店，每月多轮巡店任务
- 一家门店一次任务几十张照片，全部要人眼过一遍
- **不同专员的判定口径不一致**——同样一张照片，甲说合格、乙说不合格，门店会不服

这两件事叠加，导致：**人力成本高、标准难统一、问题发现晚**。

### 1.3 为什么选"排面缺货"作为第一个 AI 化检查项

| 理由 | 说明 |
| --- | --- |
| 业务价值最直接 | 货没摆满 = 直接损失销售机会，是零食门店高频且影响营收的偏差 |
| 视觉特征最明确 | 连续空位、缺货位无价签，比"陈列是否美观""卫生是否达标"更可判定 |
| 口径能说清 | 业务侧能明确表达"什么算没摆满"，这是 AI 化的前提 |
| 撬动的人力最大 | 它是专员逐张看照片时最耗时的检查项之一 |

## 二、问题的本质

表面问题是"能不能用 AI 识别缺货"，但真正的问题是：

> **如何把运营侧一句模糊的"货架没摆满"，翻译成一套模型可执行、专员敢复核、门店能接受、数据可验收的口径——并且在不改动既有巡店体系的前提下接进去。**

这里有三层难度：

**第一层：口径模糊**
"没摆满"到什么程度算问题？空 1 个位算不算？价签槽算不算空位？被顾客挡住看不清怎么办？——**这些业务侧自己也说不清，但 AI 化必须说清。**

**第二层：判错的代价不对称**
这不是一个推荐系统，判错会直接影响门店的奖励与处罚。而门店有申诉权。
- 在照片密集陈列里把正常间隙**误报**成缺货 → 专员被无效信息淹没 → 不再使用这个功能
- 把真实缺货**漏报** → 业务价值打折，但不直接伤害信任

**误报比漏报更致命**——这个判断贯穿了后续所有设计。

**第三层：不能动既有体系**
巡店任务派发、整改链路、申诉机制、得分规则都已经在服务数千家门店。任何对既有链路的改动都会波及门店运营。**AI 的不确定性不应该传导到既有制度上。**

## 三、我的工作路径

```text
① 定义口径          ② 设计产品           ③ 验证可行性        ④ 依据数据修正
   ────────          ────────             ────────            ────────
   把"没摆满"          AI 初筛 +            先花两天验证         层号准确率
   翻译成可执行         专员复核            最致命的假设         仅 60%
   的判定依据          的人工确认点         （模型到底行不行）   → 改判定粒度
```

### ① 定义口径

把模糊的业务诉求翻译成结构化检查项，并明确写入检查表：

| 字段 | 内容 |
| --- | --- |
| 判定依据 | 同一层货架出现连续 3 个及以上空位，且无价签或商品遮挡 |
| 合格标准 | 空位少于 3 个视为正常排面调整，不判定 |
| 分层口径 | 从上往下数，最上层为第 1 层；堆头等非层状陈列单独标注 |
| 无法判定时 | 标"不确定"交人工，不计入 AI 判定成绩 |
| 严重程度 | 高（由门店经营中心定义） |

关键取舍：**门槛定在"连续 3 个"而不是"只要有空位就报"**——因为报太多无效项会直接摧毁专员对本功能的信任，信任没了这个功能就废了。

### ② 设计产品

定位：**不新建巡店体系，只把"人逐张看照片"替换成"AI 先看一遍、人只复核 AI 的结论"。**

- **复用**既有巡店任务、图片中心、任务报表、告警中心
- **不改**任务派发、整改链路、申诉机制、得分与处罚规则
- **新增**只有三样：AI 初筛结果、复核动作与留痕、AI 表现统计

复核交互设计成三个动作：**确认 / 改判 / 补充**。其中"改判"是本功能迭代的唯一弹药来源，因此设计上明确**改判不计入专员的负面记录**——要鼓励而不是抑制。

### ③ 验证可行性

在写任何产品代码之前，先回答一个可能让整个项目失败的问题：

> **2025 年的多模态模型，能不能稳定识别出门店照片里的排面缺货？**

我搭了一套评测链路（Python + 多模态模型 API），包含：结构化输出校验、失败重试与兜底、多次采样取多数、混淆矩阵与一致性统计，并用真实巡店照片跑通。详见 [`02-产品决策与实测修正.md`](./02-产品决策与实测修正.md)。

### ④ 依据数据修正

实测发现模型**判断"有没有缺货"可靠（91.7%），但判断"是哪一层"不可靠（60%）**。

原设计是"按货架层报告缺货"，理由是"门店整改要知道补哪一层"——**这个推理本身没错，但数据不支持**。于是改为：

> **AI 负责定位到证据照片并圈出区域（这是它可靠的部分），层号降级为辅助提示，由专员或店长看证据照片自行确认。**

如果继续按层给结论，约 40% 的情况店长会照着错层号白跑一趟，然后不再信任这个功能。

## 四、方法论（这套方法可以复用到其他 AI 功能）

### 4.1 先用两天验证最可能失败的假设

AI 功能的最大风险通常不是工程实现，而是**"模型到底能不能做这件事"**。这个问题不验证清楚就投入开发，等于赌。

我的做法：**搭一个最小评测链路，用真实数据先回答这一个问题。** 成本是两天加几十块钱模型调用费，收益是避免了花两周做一个不成立的产品。

### 4.2 把"模型的不可靠"设计进产品，而不是指望它变可靠

实测发现的三个模型短板，都转化成了产品机制：

| 实测短板 | 产品对策 |
| --- | --- |
| 单次调用层号噪声率 13.3% | 多次采样取多数 |
| 36 次判定中 0 次主动标"不确定" | 画面质量预检**强制**标注不确定，不依赖模型自觉 |
| 层号准确率仅 60% | 层号降级为辅助提示，不作为结论 |

### 4.3 让基准可辩护

第一轮实验我用自己的人工判断当基准，结果**发现模型是对的、我错了**（有一张真实缺货我漏看了）。

这件事带来两个结论：
1. **在没有独立人工基准之前，任何准确率数字都不可信**
2. **连制定口径的人都会判错，恰好证明了这个功能存在的理由**——业务口径本身是模糊的，所以产品必须让别人能改判

## 六、这个案例里我做了什么（边界诚实）

**我做的**

- 把一个模糊的业务诉求翻译成结构化、可执行、可验收的检查项定义
- 设计"AI 初筛 + 人工复核"的产品链路与复核交互
- 明确产品与既有巡店体系、其他检查项、其他团队的协作边界
- 独立搭建评测链路并跑通真实数据验证
- 依据实测数据推翻并修正自己的产品设计
- 制定效果评估方案（含合格标准与不达标时的处置）

**不是我做的（不据为己有）**

- 巡店系统的整体架构、任务派发、整改与申诉链路
- 其他检查项的 AI 化
- 团队组织、上线节奏、跨部门协同
- 模型选型的最终决策与商务

**当时的技术环境**

2025 年，多模态模型进入 VLM 2.0 阶段：高分辨率切图让模型能看清货架小目标，原生多图理解让一次巡店的多张照片能放进同一上下文。**在此之前的小模型路线做不到这种泛化**——每加一个检查项都要重新标数据、重新训练；而连锁零售的检查表是常态调整的。

但也必须承认 2025 年 VLM 的三个现实限制：**计数与边界判断不稳、对光照角度敏感、结论不可复现**。这三条直接决定了我的产品设计。
